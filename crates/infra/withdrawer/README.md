# Withdrawal proving and finalization

`base-withdrawer` provides withdrawal configuration, signers, typed RPC clients, withdrawal extraction, proof verification, and the complete prove/finalize flow. Configuration validates settings without deriving keys or accessing devices. Prove and finalize submissions use `base-tx-manager` for EIP-1559 fees, replacement transactions and confirmation depth.

Supply `--l1-rpc-url`, `--withdrawal`, and exactly one signing source. `--private-key` accepts a 32-byte hex key, also available through `WITHDRAWER_PRIVATE_KEY`. `--mnemonic` accepts an English BIP-39 phrase as one quoted value or separate words, also available through `WITHDRAWER_MNEMONIC`. Conversion joins the words with single spaces and validates the phrase. `--ledger` is available only with the `ledger` Cargo feature. Mnemonic and Ledger sources use `--hd-path`, defaulting to `m/44'/60'/0'/0/0`. Paths must have at most 255 components. Each component must have an index between 0 and 2147483647, with or without a hardened suffix. Secrets have redacted debug output and parse errors. RPC URL parse errors retain the parse reason and flag name without the rejected value. `--hd-path` parse errors retain the flag name and a fixed reason without the rejected value. Other invalid-value errors retain declared flag names, but redact values and omit suggestions. A flag given with no value keeps clap's "a value is required" message. Unexpected-argument errors redact the entire token regardless of the signing source. `--version` prints the crate version. Prefer environment variables over argv to avoid exposing secrets in process listings.

`WithdrawalSigner::new(&SignerSource)` asynchronously creates a local signer or connects to a Ledger. Raw keys must be nonzero secp256k1 scalars. Mnemonics use standard BIP-39 with an empty passphrase and BIP-32 at the configured path. The signer implements `alloy_network::TxSigner<Signature>` for its address and transaction signing; `is_ledger()` identifies hardware signers. Debug output never includes signing secrets.

The optional `ledger` Cargo feature enables hardware signing through `WithdrawalSigner` wrapped in an `EthereumWallet`. Connect and unlock the device and open its Ethereum app before construction. Ledger paths must have at most 10 components. Signatures must recover to the device's address. Submissions use EIP-1559 transactions, not legacy transactions.
Each fee-bumped replacement requires a new signature and approval on the Ledger; `--tx-manager.resubmission-timeout` controls the fee-bump interval. Both `--timeout` and `--tx-manager.tx-send-timeout` keep running while you approve replacements.

`--network` selects `base-mainnet` by default, or `base-sepolia`, `op-mainnet`, or `op-sepolia`. Each preset stores its L2 endpoint, portal, and L1 chain ID: 1 for the mainnets and 11155111 for the Sepolia networks. Presets use fault proofs and discover their proof contracts from the portal over L1 RPC. For a custom network, omit `--network` and supply `--l2-rpc-url`, `--portal`, and either both `--dispute-game-factory` and `--anchor-state-registry`, or `--l2-output-oracle`. Addresses and withdrawal hashes require exact-length hex values. Custom contract addresses must not be zero. Custom networks have no expected L1 chain ID.

The custom fault-proof flags are expected addresses, not overrides: both must match the portal's `disputeGameFactory()` and `anchorStateRegistry()` values. A mismatch returns `WithdrawerError::ProofContractsMismatch` with the configured and portal-reported addresses before signer construction or transaction preparation, including dry runs.

Transaction-manager flags use `--tx-manager.*` and `WITHDRAWER_TX_MANAGER_*` environment variables. They configure fee limits, resubmission intervals, send timeouts and confirmation depth. Defaults include ten confirmations and a ten-minute send timeout. `--gas-limit` sets a minimum via `TxCandidate::gas_limit`. Both dry runs and submissions still estimate gas and use the larger of the estimate and this minimum.

`--timeout` defaults to `10m` and bounds the entire operation, including confirmation waiting. `--max-retries` defaults to 3 and `--retry-delay` to `2s`. These set the HTTP transport retry limit and initial backoff for reads and submissions, not fee replacements. Submission RPCs have an additional transaction-manager deadline, so they may stop before exhausting these retries. Durations must be positive. At most 32 retries are allowed and exponential delays must fit a Rust duration. `--dry-run` estimates without signing, broadcasting or constructing a transaction manager.

`WithdrawalRpc::new(&WithdrawerConfig)` synchronously builds `l1` and `l2` alloy `RootProvider` clients with reqwest, regardless of other enabled alloy backends. Construction performs no network I/O. Only HTTP(S) is supported. Other URL schemes are rejected without exposing the endpoint. Each HTTP attempt, including direct provider reads, is bounded by `WithdrawalRpcTransport::REQUEST_TIMEOUT` (30 seconds), capped at half the configured `timeout` so a hung request can be retried before the operation deadline. Use standard `Provider` methods directly for contract calls, storage proofs, receipts, and pending nonces, such as `rpc.l1.get_transaction_count(address).pending().await`.

Direct reads through `WithdrawalRpc` can use the full transport retry budget within the overall operation timeout. Transaction-manager RPC calls, including broadcasts and receipt queries, are additionally bounded by `--tx-manager.network-timeout`, which defaults to `10s`. This deadline covers the entire call, including HTTP attempts and backoff. With retries enabled, the submission provider caps each attempt at one third of the network timeout remaining after the initial retry delay, while retaining the 30-second and half-operation-timeout caps. This leaves room for a retry and its backoff. Configuration rejects retry delays that leave no attempt budget. With retries disabled, attempts are capped at half the network timeout instead. Later retries may still exceed the deadline. Receipt polling and fee replacements are separate transaction-manager behavior, not transport retries.

The transport retries connection failures, request timeouts, HTTP 429/5xx regardless of response body, and single JSON-RPC responses recognized as retryable by alloy, including rate limits and `header not found`. On successful HTTP responses, execution reverts are not retried, even when their reason mentions a rate limit. Batch responses preserve each item's outcome without retrying individual JSON-RPC errors. `max_retries` counts attempts after the first, with delays of `retry_delay`, twice that delay, and so on. This uses a small tower service because alloy's `RetryBackoffLayer` uses a fixed base delay. Requests, including whole batches on transport failures, are replayed unchanged. Use these clients for reads and already signed submissions, not non-idempotent RPC methods. Transport errors strip URLs and HTTP bodies while retaining safe source errors. HTTP client tracing is disabled to keep endpoint credentials out of spans. JSON-RPC envelope parse failures in `WithdrawalRpcTransport` retain only the error category and location. Alloy's typed-result decoding errors include the server's response content, as do JSON-RPC error messages.

`PreparedWithdrawalTransaction::prepare(&config, &rpc, sender, target, calldata)` estimates a zero-value dry-run candidate without accessing signing material. It checks the expected L1 chain ID, obtains the latest base fee and priority fee, applies configured minimums, and estimates gas with `gas_limit` as a floor. The fee cap is the priority fee plus twice the base fee. Preparation is bounded by `rpc.timeout`, with credential-safe source errors.

The prepared `candidate` contains the target, calldata and gas limit. `maximum_gas_cost()` returns the gas limit times the estimated fee cap in `U256` wei. This is an estimate, not a promise of the eventual transaction fee after replacements.


`WithdrawalRpc::l2` uses `base_common_network::Base`, so provider receipts include deposit transactions of type `0x7e`. Pass an L2 receipt to `Withdrawal::from_receipt` to extract every `MessagePassed` event from `Predeploys::L2_TO_L1_MESSAGE_PASSER` in log order. Other emitters and event signatures are ignored. Missing withdrawals, missing block numbers, malformed events, and emitted hashes that disagree with the decoded fields return typed `WithdrawalError` variants. Each withdrawal contains a sol `WithdrawalTransaction` and its `u64` inclusion block number. `hash()` computes the ABI field commitment; `slot()` derives its `sentMessages` mapping key.

`Withdrawal::verify_proof` takes an L2 RPC header, an EIP-1186 account proof, and an onchain output root claim. It recomputes the header hash locally, authenticates the message passer account against the header state root, and verifies exactly one storage proof for the withdrawal slot with value one. The output commitment uses `base_protocol::OutputRoot` and must match the claim. Success returns `VerifiedWithdrawalProof` with the sol `OutputRootProof` and storage proof nodes for the portal's `proveWithdrawalTransaction` arguments. Trie and event-decoding errors retain their sources. Storage proofs are accepted with inline nodes either omitted, as Geth returns them, or kept as separate elements, as reth returns them; the returned nodes always keep them separate. Verification does not fetch data, establish the claim's validity or finality, or submit transactions. Dispute games are permissionless, so callers must check that the game is proper, respected, and not resolved as `CHALLENGER_WINS` before relying on its claim.


`WithdrawalRpc::broadcast` and `wait_for_receipt` remain available for signed envelopes, but the prove/finalize flow no longer uses them. Broadcast errors do not prove that a transaction was not submitted. Receipt polling checks every two seconds until inclusion or the configured timeout. Direct Ledger signing still rejects legacy chain IDs whose truncated EIP-155 parity cannot be decoded reliably.

## Prove/finalize flow

Construct `Withdrawer::new(config)` and call `run().await`. One timeout covers provider construction, proof-contract discovery, signer construction, receipt fetching, decisions, proof verification, preparation, signing, broadcast, and inclusion.

For fault proofs, `run` reads `disputeGameFactory()` and `anchorStateRegistry()` from the configured portal once each before constructing the signer, including dry runs. Every withdrawal's status, game search, eligibility, and finality checks use those resolved contracts for the rest of the run. RPC and ABI failures return typed, redacted errors with safe sources; a zero address returns `WithdrawerError::ZeroPortalProofContract`. Portals without these views fail rather than falling back to static addresses. Legacy output-oracle runs do not perform these reads.

The flow processes withdrawals in receipt log order through one `SimpleTxManager` built with `from_wallet`, closed at the end. Private keys, mnemonics and Ledger signers all use an `EthereumWallet`. Before each untracked `TxManager::send`, it resets the manager's nonce cache to read the node's pending nonce again. This accounts for other jobs sharing the signer and for cancelled sends that may not have reached the node. Submissions through this manager must be serialized. Each send waits for the configured confirmation depth. Broadcast failures, reverted receipts and timeouts, including cancellation by the operation deadline, return `WithdrawerError::Unconfirmed` with every L1 hash broadcast for that send and a redacted source error. The submission transport records `keccak256(raw)` before forwarding each `eth_sendRawTransaction` request, including batches, and deduplicates retries in a shared `BroadcastJournal`. A timeout does not undo a submission. Before rerunning, check the reported hashes for inclusion or wait for them to mine or drop. Status reads use only the latest mined L1 state, so a rerun while a transaction is pending can submit a duplicate at the next nonce that reverts and spends gas after the first mines.


For lower-level reads, call `Withdrawer::resolve_proof_system(&rpc)` once and retain its `ResolvedProofSystem`. Pass it to `status(&rpc, proofs, &withdrawal, submitter)`, `proving_output`, and `prove_calldata` to reuse the same contracts. `status` performs only reads against the latest mined L1 state. It does not prepare, sign, or submit transactions. `run` uses the same status API with the signer's address.

`WithdrawalStatus` separates onchain decisions from transaction submission. `Finalized` does nothing, `Prove` requires a new proof, `Finalize` permits execution, and `Paused` waits for the anchor state registry (fault proofs) or legacy portal (output oracle) to be unpaused before proving or finalizing. `NotReady` reports an earliest known L1 timestamp with a flag for an unresolved game. The game must resolve before its finality delay can start, so that timestamp is not a promise of readiness.

`WithdrawalOutcome` records each withdrawal's hash, decision, and confirmed L1 transaction hash, if any. The flow logs the decision even when it sends nothing.

Fault-proof state uses `provenWithdrawals(hash, signer_address)`. While the anchor state registry or legacy portal is paused, withdrawals wait without replacing proofs. When the registry is unpaused, blacklisted, retired, improper, unrespected, and challenger-winning games invalidate a fault proof. In-progress games retain their proofs but cannot finalize. Legacy proofs are invalidated when their stored output root differs from the oracle, or when the stored output's lookup reverts. Other legacy RPC errors fail without submitting.

Proving walks factory entries backwards from `gameCount() - 1`. It fetches the withdrawal's L2 block timestamp once and stops the walk at the first game of any type created before that timestamp. That game and all older games predate the withdrawal and cannot honestly cover it. The flow considers games of any type, including earlier types that were respected when the games were created. Each covering game costs three contract reads during the walk: `gameAtIndex`, `extraData` for its claimed L2 block, and `isGameFinalized`. The flow skips malformed or overflowing block numbers before the finality read. It also skips non-covering games, since games can be created out of L2 block order. Eligibility checks and the `rootClaim` read are deferred until a candidate is about to be verified. This applies to finalized games too, since finality alone does not imply eligibility. Ineligible candidates are skipped without a warning.

The walk tries to verify covering, eligible games that the `AnchorStateRegistry` reports as finalized, returning the newest one that verifies. Only proof maturity remains for those games. It saves non-finalized candidates as their factory index, proxy, and claimed L2 block without reading eligibility or `rootClaim`. If no finalized game verifies before the timestamp cutoff or the end of the factory, it tries the saved candidates from oldest to newest and returns the first that verifies, since the oldest game should resolve first.

Some L2 RPCs, including the default `base-mainnet` endpoint, only serve recent state. Once transport retries are exhausted, the first RPC failure fetching a candidate's L2 header or `eth_getProof` makes the flow assume historical state is unavailable. It stops the backward walk or abandons the oldest-first order and tries the remaining untried saved candidates from newest to oldest. It returns the first that verifies. A second proof RPC failure stops the run immediately with that error, so at most two candidates incur RPC stalls and their transport retries. If the fallback exhausts its candidates, the first RPC error is returned.

Games with fewer than 32 bytes of `extraData`, block numbers exceeding `u64`, unavailable claimed L2 blocks, or failed local proof verification are skipped with a warning containing the game index, proxy, and redacted reason. These non-RPC failures do not change the selection order, including during the newest-first fallback. Proof RPC failures also warn with the game index, proxy, and redacted error. If no candidate verifies and no proof RPC failure occurred, the flow returns `WithdrawerError::NoCoverage`. Errors from factory, registry, and game contract reads, contract-response decoding errors, and the shared operation deadline still stop the run. Legacy selection returns `WithdrawerError::NoCoverage` when no published commitment covers the withdrawal.

Before selecting a commitment, the flow fetches its L2 header and message passer `eth_getProof`, then calls `Withdrawal::verify_proof` against the published root. Fault-proof games that fail verification do not prevent trying the next candidate in the selection order; legacy verification failures return an error. No prove transaction is prepared without a verified proof. Fault-proof finalization requires proof maturity and ASR game finality, followed by the portal's authoritative `checkWithdrawal` call. Legacy finalization checks the proof and output ages against the latest L1 timestamp, not the local clock or L2 time. Both apply the portal's strict timestamp boundary. Each invocation performs only one step per withdrawal; rerun it after proving and waiting for finality.

After a successful finalize receipt, the flow checks the configured portal's `WithdrawalFinalized` event for this withdrawal hash. A false `success` returns `WithdrawerError::TargetCallFailed`; the portal has consumed the withdrawal and it cannot be retried. A missing matching event returns `WithdrawerError::MissingFinalizationEvent`. Both errors include the withdrawal hash, confirmed L1 transaction hash and all attempted replacement hashes.

Flow RPC errors use `WithdrawalRpcTransport::redact_diagnostic` to remove server-supplied messages and data that might echo credentials. They retain the typed transport source and JSON-RPC error code. Transaction submission and receipt polling run inside tx-manager over the redacting `WithdrawalRpcTransport`. Retry classification runs on the raw error. Submission errors preserve fixed transaction-manager classifications so fee replacements and nonce handling still work without exposing server diagnostics. Execution-revert classification retains only the code and the "execution reverted" marker. Only on a transport retry of `eth_sendRawTransaction`, "already known" returns the local hash; "nonce too low" returns it only if `eth_getTransactionByHash` finds that hash. First-attempt rejections still fail. Contract and withdrawal event ABI decode errors identify the call or event and error kind without response data. At the flow boundary, account and storage proof errors replace value-mismatch payloads with their error kind and retain safe proof errors as sources. The same redaction applies to warnings for skipped games.

Dry runs prepare the same prove or finalize call as a submission and log its target, calldata length and selector, gas limit, and maximum gas cost. They never sign or broadcast. Gas estimation cannot detect a failing withdrawal target call because the portal can finalize successfully even when that call fails. Already finalized, paused, and not-ready withdrawals do not prepare transactions. The [withdrawer binary](../../../bin/withdrawer/README.md) provides the CLI for this flow.

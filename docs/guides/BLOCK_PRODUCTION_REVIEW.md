# Block Production Halt/Stall Critical Findings

This guide is for automated Claude reviews of block-production-sensitive changes. Treat a PR as block-production-sensitive when it touches builder, execution, precompile, payload assembly, state-root, tx selection, metering, payload/data transport, or flashblocks publishing paths.

The scenarios below are known high-risk patterns, not an exhaustive list. Use engineering judgment to flag analogous changes that could halt block production, stall payload finalization, prevent validator re-execution, or indefinitely exclude valid transactions, even when the exact code path is not named here.

For any unmitigated change that can introduce, widen, or obscure one of the trigger conditions below, leave an inline **Critical** finding. A finding should name the triggering input/state/config, the affected code path, the propagated error or panic, the halt/stall mode, and the missing mitigation or test.

## Mandatory Payload/Data Boundary Gate

Any PR that adds, replaces, or changes a path that moves block-production data across an I/O boundary must answer the size-limit questions below before it can be considered safe. This applies even when the change is framed as a latency optimization, an encoding change, a fallback path, or a way to bypass a previous size cap.

Block-production data includes blocks, payloads, flashblocks, batches, frames, transactions, receipts, state updates, requests, responses, and commit messages. I/O boundaries include in-process channels, websocket publishers, RPC and gossip messages, HTTP handlers, database writes, batcher/blob/calldata frames, conductor payload commits, and external services.

For each changed boundary, require the review to identify:

1. The maximum size accepted by every downstream hop, including implicit framework, proxy, RPC server, HTTP server, database, queue, raft/consensus, or service-body limits.
2. Whether the limit applies to serialized, encoded, compressed, uncompressed, framed, JSON-expanded, or raw bytes.
3. Where the producer enforces that limit before a locally valid payload can be built, committed, published, or retried indefinitely.
4. What happens at exactly the limit and just over the limit, including fallback, finalization, retry, and operator-visible error behavior.
5. Tests or documented evidence covering at-limit and over-limit payloads for the production boundary. A skipped/manual/e2e-only test is not enough unless the PR also explains the production limit and why unit or integration coverage is impossible.

Leave an inline **Critical** finding if a PR changes a block-production data boundary but does not identify the downstream maximum size, does not enforce the bound before or at the production boundary, removes the only boundary test, or lacks at-limit and over-limit coverage. This is especially important when a PR introduces a new transport or encoding specifically to avoid a previous size cap: the new transport's own limit must be documented and tested, not assumed to be unbounded.

## Review Checklist

When a PR touches a block-production-sensitive path:

1. Identify whether the changed code can run while building, finalizing, publishing, or re-executing a block.
2. Trace all new or changed `?`, `map_err`, `unwrap`, `expect`, `panic!`, channel send, timeout, cancellation, and error conversion paths.
3. For each path, determine whether the trigger is user-controlled transaction input, payload attributes, chain data, DB/provider state, fork config, runtime config, or network/client behavior.
4. If block-production data crosses any new or changed I/O boundary, apply the Mandatory Payload/Data Boundary Gate and require explicit downstream max-size analysis plus at-limit and over-limit coverage.
5. Confirm the code either produces a valid payload, intentionally rejects the payload with consensus/proof parity, or degrades without blocking finalization.
6. Require targeted tests for boundary inputs and for both txpool-building and derived-attributes modes when behavior differs.

If the PR lacks enough context to prove the changed path cannot halt or stall block production, leave a **Critical** finding requesting the missing analysis or tests.
